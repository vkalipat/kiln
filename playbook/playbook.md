# kiln playbook

Bullets are numbered and carry counters the reflector updates. Delta edits only; never rewrite this file wholesale.

## lenses
- L1 [helpful:0 harmful:0] Invert a shared assumption from the tensions list and ask what becomes possible.
- L2 [helpful:0 harmful:0] Recombine two atoms that never co-occur in the landscape and make the combination coherent.
- L3 [helpful:0 harmful:0] Transfer the core mechanism of a distant domain that solves a structurally similar problem.

## frame
- F1 [helpful:0 harmful:0] Name the idea shape (research, product, creative) explicitly; the value axis depends on it.
- F2 [helpful:0 harmful:0] The obvious list should have at least five entries; fewer means the search was not honest.

## discover
- D1 [helpful:0 harmful:0] One question per scout. Broad questions return broad findings.
- D2 [helpful:0 harmful:0] Record what was tried and failed with the stated reason; it is the best source of tensions.

## ideate
- M1 [helpful:0 harmful:0] Combine two frontier ideas: take the mechanism of one and the user or setting of the other, and make the join coherent rather than stapled.
- M2 [helpful:0 harmful:0] Specialize to a narrower user: pick one frontier idea and rebuild it for the smallest group whose problem it fits exactly.
- M3 [helpful:0 harmful:0] Generalize the mechanism: state what a frontier idea's mechanism really does, then apply it to the widest class of problems it still fits.
- M4 [helpful:0 harmful:0] Swap the domain: keep a frontier idea's mechanism and move it to a distant domain from the landscape that has the same structural problem.
- M5 [helpful:0 harmful:0] Turn the failure reason into a feature: take a frontier idea's strongest failure reason and design the idea that needs that condition to be true.

## form
- FM1 [helpful:0 harmful:0] Refine the plan beyond its first draft. Why: Critique and revision remove scope and verification defects before work begins.
- FM2 [helpful:0 harmful:0] Prefer shell or file acceptance checks; use manual checks only where no executable oracle exists, and never for the first feature. Why: Executable evidence is strongest while some outcomes genuinely require human inspection.
- FM3 [helpful:0 harmful:0] The first milestone is what a user could see.

## build
- B1 [helpful:0 harmful:0] The harness must select either a fresh builder session per feature or one append-only session across features. Why: Both build arms are deliberate and preserve the same feature contract.
- B2 [helpful:0 harmful:0] Treat repository state plus the current feature contract, audit, and progress context as inherited build inputs. Why: Those durable inputs are required evidence, not hidden state.
- B3 [helpful:0 harmful:0] The auditor must record verified evidence and next-session notes for later builder sessions to consume as cross-session memory. Why: The harness owns that channel while the builder remains focused on repository work.
- B4 [helpful:0 harmful:0] Regressions from earlier work are the long-horizon failure.
