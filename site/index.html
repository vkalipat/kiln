Overview

Kiln is a terminal harness for research, ideation, and implementation. It connects frontier models to local tools, persistent sessions, and scoped collaborators.

  • Work in your project’s terminal and continue the same session across follow-ups.
  • Delegate independent tasks with clear ownership and reviewable handoffs.
  • Inspect the resulting files, sources, and verification records.

Install

You’ll need Git and Bun 1.3.14 or newer. Install from the source repository:

git clone https://github.com/vkalipat/kiln.git
cd kiln
bun install --frozen-lockfile
bun link

Connect a provider

kiln auth login
kiln doctor --json
  • Choose subscription sign-in or API-key access in the login flow.
  • Run doctor to inspect your local configuration.
  • Open a terminal in your own project, then run kiln.

To update an existing installation, open the Kiln checkout and run git pull --ff-only, then bun install --frozen-lockfile and bun link. Restart Kiln after updating.

Run a task

Start with what should exist when the work is done. Give Kiln enough context to make decisions without prescribing every step.

  • Name the deliverable. A working feature, research report, ranked shortlist, or tested prototype.
  • Define the scope. The project, source material, constraints, and decisions you want to retain.
  • Make “done” observable. Describe the behavior, evidence, or checks that would satisfy the request.
  • Steer as you go. A message during work updates the task. A follow-up continues the same session.

Build a CSV importer in this project. Handle missing headers and malformed rows. Keep the existing UI style. Finish when the relevant tests pass and the import flow works in the rendered app. Report any remaining gaps.

To start a task directly from the command line:

kiln task "Implement the importer and verify malformed input handling" --cwd .

Describe the outcome, quality requirements, and constraints. When independent work benefits from delegation, Kiln composes task-specific responsibilities with separate file scopes, dependencies, and acceptance checks. The parent operator reviews the handoffs and integrates the result.

Research & ideation

Ask for sources, competing approaches, assumptions, and a test that could change the decision. Task-specific teams can research alternatives, generate ideas, run probes, and review the evidence.

Implementation

Describe the behavior and constraints. Let the operator choose the steps, use tools, inspect results, and repair failures within that scope.

For additional controls, see the workflow commands.

Models and reasoning

The operator proposes responsibilities, goals, and acceptance checks for the task. Jev selects compatible models and effort using the task, reviewed evidence, and compute cost. Smaller models and lower effort remain eligible; Kiln applies the saved assignment when dispatching a worker.

  • The roles command shows legacy defaults. Resource routing uses the compatible catalog rather than a preset team.
  • Automatic effort adapts to the task. Explicit model and effort choices remain authoritative. xhigh appears as ultra in the TUI.
  • Routes stay stable inside tool loops and can change at task boundaries or explicit routing requests. Existing sessions retain their saved policy.
kiln model routing adaptive
kiln mode set auto
kiln mode show

Use kiln mode set auto for Jev effort selection, or a level such as kiln mode set high to pin it. Catalog and benchmark updates remain explicit.

Integrations

Connect Jev for constrained decisions or Hindsight for curated project memory.

Jev

Jev selects model and effort through separate questions in one request, and chooses among task-specific role alternatives. It also supports bounded browser actions and research passage classification. The operator remains responsible for planning and assessing the work.

kiln auth key jev
kiln integrations jev enable
kiln doctor --require jev --json
  • Enter the key in the masked prompt.
  • Browser workflows operate on an existing, owned native tab with explicit actions and outcome checks.
  • Research workflows capture bounded sources, citations, contradictions, and unknowns.
  • New settings apply to new sessions.

Hindsight

Use project memory when you need curated knowledge across runs. Set up a running Hindsight server and an explicit project bank, then choose what to retain.

kiln memory status --url http://127.0.0.1:8888 --bank example-project

Configure authentication with kiln auth key hindsight when your server requires it.

Resume and monitor

Keep the run ID from the output. Resume that run to retain its context, artifacts, model selections, and recorded usage.

kiln task resume RUN_ID "Continue the remaining checks"

# Or reopen it in the terminal interface
kiln --run RUN_ID
  • Press Esc in the TUI to request a pause. Ctrl + C interrupts a CLI task.
  • kiln task resume RUN_ID without a message only reports retained state.
  • Uncapped sessions keep usage accounting and loop monitoring.
  • Existing runs retain their saved allocations. A new default does not change a resumed run.
# Inspect defaults and a run's latest monitor snapshot
kiln task limits
kiln task monitor RUN_ID --json

To remove aggregate dollar and active-time limits for future native sessions, explicitly run kiln task limits --uncapped.

The monitor reports repetition, context growth, and recorded usage.

Usage notes

  • Service access. doctor and memory status inspect local configuration. Live authentication, quota, and service health depend on your provider or server. If Jev is unavailable or uncertain, Kiln retains an eligible current route or uses a conservative reviewed fallback, recording the source.
  • Compute and cost. Submitting a task can use paid provider access. Uncapped sessions remove aggregate dollar and active-time limits; provider, tool, and concurrency limits still apply. In-flight work can exceed a finite allocation.
  • Result quality. Review delivered artifacts, sources, checks, and unresolved gaps. Monitor readings, model rankings, and individual Jev decisions inform that review; they do not establish that the whole task is complete.
  • Workspace access. Shell and file tools act with your local permissions. Specify the task’s scope, authorize external actions deliberately, and enter credentials through the authentication prompts.
